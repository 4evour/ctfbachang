# Vulfocus 题解卡片库

## 用途
把题库题目整理成 Codex 比赛时能快速调用的利用步骤。核心是步骤、该漏洞特有的排坑，以及能支撑这些步骤的专业题解和官方资料；卡片不负责填写 Flag 答案。

## 文件
- `cards/`：每题的操作链、成功信号、特有排坑和来源编号。
- `sources/`：每题 `_meta.md`，保留可打开的原文链接及其用途；不下载整篇原文。
- `index.csv`：题名、CVE、内部端口、卡片路径、有效来源链接数。
- `batches/progress.csv`：题目状态、来源数和下一题。
- `WORK_LOG.md`：只记重要规则变化与阶段进展，保证长任务可续接。
- 原始题库 CSV、样本 ZIP、个人实战手册及已摘录的原文副本仅保留在维护者本地，不纳入公共仓库；`index.csv` 保留题名、CVE、端口和整理状态。

## 执行顺序与返工边界
- 当前进度只以 `batches/progress.csv` 为准，不在本文件硬编码“已完成到第几题”，避免状态过期。可同时处理最多两道相邻待整理题；每个执行者只写自己负责的卡片和来源目录。
- 已完成的卡片视为冻结。工作流更新只用于后续新卡片，不触发旧卡片批量返工；只有用户明确要求，或发现具体事实错误会误导解题时，才针对性修改。
- 每次结束只更新当前题及进度，不顺手重审其他已完成卡片。

## 单题工作流
1. **只取当前题上下文**：先读 `index.csv` 当前行；维护者本地有原始题库时再对照原题行，然后读本题卡片、`sources/<本题目录>/_meta.md`；只有必要时才查 `用户真实解题手册.md` 中与本题直接相关的记录。不要把整套卡片/来源一次性灌入上下文。
2. **只搜对应题解**：CVE/CNVD 题先用完整编号组合“复现 / 题解 / WP”搜索；无编号题按题名、镜像名搜索。只打开能确认与该编号/产品版本直接相关的专业题解、PoC 和必要官方公告，不扩展到无关网页；优先同题 Vulfocus WP，其次同漏洞/同版本技术博客。链接必须能说明具体请求、参数、Payload、利用顺序或特有坑。
3. **补官方资料**：查厂商/项目官方公告、文档或修复说明，核对漏洞类型、影响版本、前提和接口。官方资料用于定边界；具体操作步骤优先由专业题解支撑。
4. **整理成最短可执行链**：按实际顺序写请求入口、参数/Payload、命令和成功信号。每个操作步骤及关键排坑后标 `[S#]`；来源清单用同编号说明该来源具体支持哪一步。端口、路径、编码、请求头、认证、版本或目标库语法等特有条件要写清。
5. **排坑只写本题特有且会导致失败的点**：不写通用安全提醒、模板免责声明或空泛“先确认环境”等内容。来源确有多个版本/条件差异时，说明对应区别。
6. **来源不足时**：简短注明“未找到直接题解”；用官方资料和 PoC 整理最短链路，并明确 PoC/模板支撑了哪些步骤。无漏洞的环境题不编造利用链；资料确实不足就如实留下，不用通用侦察步骤凑卡片。
7. **Flag 不属于卡片**：不写 Flag 值、存放位置、猜测路径、搜索 Flag 命令，也不写“Flag 未知/未验证”等填充段。没有真实比赛实例时，卡片只到漏洞利用成功信号为止；用户提供的实战笔记另行保留，不从公开题解推断 Flag。
8. **批量同步**：卡片与来源清单使用同一组 `[S#]` 链接；`index.csv` 的来源数只统计有用且不重复的外部原文链接。并发卡片完成后由主流程统一更新 `index.csv`、`batches/progress.csv` 和 `WORK_LOG.md`，再继续下一组；不得为并发写入共享表。

## 卡片内容基准
一张卡片只保留：**一句话打法 / 操作步骤 / 本题特有排坑 / 来源**。前提、适用版本和成功信号放在相关步骤附近；不另设 Flag、实测状态或“未知事项”填充章节。步骤要够短，读者不确定时可沿 `[S#]` 回到原文。

不做靶场实测，不下载整篇原文。以上标准从当前未完成题开始执行；旧卡片保持现状，不因格式或新标准自动返工。
